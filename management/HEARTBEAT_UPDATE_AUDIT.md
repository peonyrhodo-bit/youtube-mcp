# Технический разбор: обновление heartbeat и риск конкурентных записей

Дата: 2026-11-19. **Статус: подтверждён путь ошибки, риск гонки требует воспроизводящего теста.** Код production не менялся.

## Прослеженный путь

1. `server.py:_director_run_heartbeat` вызывает `runtime.memory.update_run(run_id, fields={})` каждые ~60 секунд.
2. `memory/director_adapter.py:update_run` добавляет `project_id` и `updated_at`, передаёт запись через `_call_off_thread(self.memory.update_run)`. При ошибке исключение поднимается вверх.
3. `memory/supabase.py:update_run` **сначала делает GET `select('data_json').eq('id',run_id).limit(1)`**, затем в Python объединяет JSON и передаёт **весь** `data_json` в PATCH вместе с отдельными полями. Это объясняет, почему в логе heartbeat непосредственно перед ошибкой виден успешный GET: следующий сетевой этап — PATCH.
4. Render traceback run 206 показывает `httpcore.ReadError: [Errno 11] Resource temporarily unavailable` в HTTP/2-транспорте при вызове heartbeat. Нужен дополнительный точный фрагмент трассировки, чтобы окончательно привязать исключение к PATCH, а не иному вызову.

## Выявленный риск

Чтение JSON → объединение в приложении → запись всего JSON **не является атомарным обновлением**. Если параллельно другой обработчик меняет `data_json` той же строки, heartbeat теоретически может перезаписать часть изменений устаревшим снимком. Это **риск по анализу кода, а не доказанная потеря данных**.

## Существующие тесты

`tests/test_director_run_lifecycle_storage.py` проверяет объединение полей и отсутствующий ID, но не сетевой сбой между GET/PATCH, не конкурентное обновление и не реальную параллельность heartbeat с финализацией. Нельзя считать эти случаи покрытыми.

## Безопасный план проверки для Codex после разрешения

- Добавить тест с ошибкой HTTP-транспорта на GET и PATCH; убедиться, что сбой виден и heartbeat не создаёт новые запуски.
- Добавить конкурентный тест: heartbeat и финализация меняют одну строку; итоговые `status`, `finished_at`, `result` и `updated_at` не должны теряться.
- Исследовать атомарное обновление heartbeat только отдельного столбца `updated_at` с проверкой активного статуса/владения циклом, без чтения и перезаписи `data_json`. При необходимости синхронизировать JSON и столбцы отдельно, но не нарушать существующие потребители.
- Проверить, что ошибку связи можно повторить безопасно и ограниченно, а статус завершённого цикла не возвращается в `running`.
- Не делать схему/миграции, деплой, реальные YouTube-вызовы без отдельного согласования.

## Критерий завершения

Изолированная регрессия воспроизведена, минимальное исправление проходит тесты; после отдельного разрешения на деплой проверены логи и долговременные записи. До этого пункт master plan остаётся открытым.

## Сопоставление с финализацией и тестами (2026-11-19)

- `server.py:_execute_autonomous_cycle_locked` сначала помечает `partial/persisting_result`, сохраняет решение/рекомендацию/результат/событие, затем выполняет `update_run` с конечными `status`, `finished_at`, `current_step` и `result`. Фоновая задача heartbeat отменяется **после** выхода из этого блока, в `finally`. Значит heartbeat может работать одновременно с промежуточной и финальной записью.
- `memory/supabase.py:update_run` использует read-modify-write полного `data_json`. При конкурентных вызовах возможно устаревшее содержимое JSON; отдельные колонки `status`/`finished_at` heartbeat не перезаписывает, поскольку его payload содержит только `project_id` и `updated_at`. **Уточнение:** опасность касается прежде всего `data_json` и согласованности JSON с колонками, а не доказанного отката отдельной колонки `status`.
- `tests/test_director_run_lifecycle.py` уже имеет тесты успешной финализации, частичного сохранения, конкурирующих стартов и защиты от повторного запуска; `tests/test_director_run_lifecycle_storage.py` проверяет merge. **Пробел уже существующих тестов точнее:** нет проверки пересечения *heartbeat update* с *final update* на настоящем Supabase read-modify-write и ошибки HTTP/2 между GET и PATCH. Не дублировать существующие тесты.
- Для регрессии достаточно fake backend с управляемыми барьерами: heartbeat читает старый JSON; финализация сохраняет `result/status`; heartbeat продолжает PATCH старого JSON. Ожидаемый тест должен показать потерю вложенного `result` в `data_json` при сохранённых отдельных колонках. До воспроизведения это **сценарий риска**, не установленный факт production.
- Второй тест: принудительная `httpx.ReadError` в `backend.update_run`, проверить журналирование heartbeat и повторную попытку без создания нового `run_id`.
